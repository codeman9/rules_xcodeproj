# SwiftUI Previews

## Overview

rules_xcodeproj supports SwiftUI Previews in Build-with-Bazel (BwB) mode using
the **XOJIT architecture** introduced in Xcode 16. Previews work by having Bazel
build real products while Xcode recompiles only the preview thunk — a small
Swift file that wraps your `#Preview` — and JIT-links it against the
Bazel-built binaries.

**Requirements:**

- Xcode 16 or later
- Build-with-Bazel mode (not Build-with-Xcode)
- iOS simulator targets (device targets are not supported by Xcode for XOJIT previews)

Preview support is disabled by default. To enable it, set `enable_previews = True`
in your `xcodeproj` rule:

```starlark
xcodeproj(
    name = "xcodeproj",
    enable_previews = True,
    top_level_targets = [":App"],
)
```

This adds several Swift compiler flags (`-enable-implicit-dynamic`,
`-enable-private-imports`, `-enable-dynamic-replacement-chaining`) and build
settings (`ENABLE_DEBUG_DYLIB`, `ENABLE_XOJIT_PREVIEWS`) that affect all builds,
not just preview builds. The `-enable-implicit-dynamic` flag in particular makes
all Swift declarations dynamically dispatchable, which has a minor performance
cost.

## How It Works

In normal BwB mode, Bazel builds the real binaries and Xcode's compile/link
phases are no-ops (tool wrappers like `swiftc_stub` and `clang.ld` create
placeholder files instead of invoking real compilers).

When you open a SwiftUI Preview, Xcode's preview system:

1. Reads the target's link command line from `link.params` (a response file
   generated by `link_params_processor.py`) to understand what libraries the
   target depends on.
2. Compiles a **preview thunk** — the `swiftc_stub` detects this and passes
   through to the real Swift compiler.
3. JIT-links the thunk against the Bazel-built framework/dylib binaries already
   present in DerivedData.

For **executable targets** (apps), Xcode 16+ also creates a debug dylib
architecture (`ENABLE_DEBUG_DYLIB = YES`), which splits the app into a stub
executor, a `debug.dylib` containing compiled code, and a `__preview.dylib`
for interposition. The `clang.ld` wrapper passes through for these link tasks
so real Mach-O files are created.

## What Works

| Target Type | Preview Support | Notes |
|---|---|---|
| Dynamic framework (`ios_dynamic_framework`) | Full | Bazel-built `.framework` used directly |
| App (`ios_application`) | Full | Uses debug dylib architecture |
| Static library (`swift_library`) | Full | `clang` and `libtool` wrappers enable static lib analysis |
| ObjC framework | Full | Works through dynamic framework embedding |
| SPM dependency (via `rules_swift_package_manager`) | Full | e.g., `swift-collections` |
| Framework with transitive xcframework dep | Full | e.g., Showcase → PreviewKit → FirebaseAuth |

## Known Limitations

- **Static library + binary dep type metadata**: Static library targets that
  transitively depend on binary-only dependencies (e.g., xcframeworks) cannot
  JIT-link type metadata symbols like `TypeName.self` for types from those
  binary deps. `import` and normal usage works; only explicit type metadata
  access (`Auth.self`, `FirebaseAuth.Type`) in preview code may fail. Workaround:
  avoid `TypeName.self` expressions in `#Preview` blocks for types from binary
  dependencies.

- **Device targets**: Xcode only supports XOJIT previews on the simulator.

- **Custom toolchains**: The current implementation assumes the default Xcode
  toolchain (`XcodeDefault.xctoolchain`). Custom toolchains are not yet
  supported.

## First Build Requirement

After generating (or regenerating) the Xcode project, you must do one full build
(**Cmd-B**) before previews will work. The preview canvas may show an error about
a missing `debug.dylib` or similar if you try to preview before building.

This is only needed once after project generation. Subsequent **Clean Build
Folder** operations do not require a manual rebuild — the preview canvas will
trigger a build that completes quickly because Bazel's cache is still warm.

## Troubleshooting

### `CouldNotParseLinkCommandLine: Could not parse linker command line`

This error typically appeared with the old `ld` wrapper name. The preview
system's linker argument parser treats `ld` as ld64 and misinterprets
`-target` as a file path. The `clang.ld` rename fixes this.

If you still see this error, ensure your project has been regenerated with the
latest rules_xcodeproj so the `LD` build setting points to `clang.ld`.

### Preview canvas shows "Cannot preview in this file"

- Verify you are targeting a simulator, not a device.
- Verify the file contains a `#Preview` macro or `PreviewProvider`.
- Check the diagnostic report: **Editor → Canvas → Diagnostics** or look in
  `~/Library/Logs/DiagnosticReports/` for crash logs prefixed with your app name.

### JIT runtime linking failure

This usually means a symbol is missing from the libraries visible to the JIT
linker. Common causes:

- A transitive binary dependency's symbols aren't available for JIT linking
  (see Known Limitations above).
- The `link.params` file is stale — try a clean build (`Product → Clean Build
  Folder`) and then rebuild.

### Crash in `__previewsInjectionPerformFirstJITLink`

Check the crash report in `~/Library/Logs/DiagnosticReports/`. This typically
indicates the JIT linker failed to load or register a pseudodylib. Try:

1. Clean DerivedData for the project.
2. Rebuild from Xcode.
3. Verify framework binaries exist in
   `DerivedData/.../Build/Products/.../Frameworks/`.
